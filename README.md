# Magic Road：视觉世界模型与硬件加速

当前从可验证的视觉功能出发，先检验识别与记忆，再依据实验决定模型和硬件实现。新增 **V0 遮挡记忆实验**；早期的 **P1 桌面仿真数据与解析基线**、**P2 首轮桌面视觉预测模型试训**和 **Minecraft M0 离线数据契约与检查器**保留供参考。P2 尚未超过简单对照，下文 Minecraft 到 RTL 的规划尚未实施。

## V0：遮挡与记忆

在普通电脑上运行，复用现有 NumPy、Pillow 和桌面背景生成器：

```powershell
$env:OPENBLAS_NUM_THREADS='1'
python software/occlusion_memory.py --out artifacts/occlusion-memory-v0
python software/test_occlusion_memory.py
```

默认种子 `20261024`，生成 100 对红／蓝经历，以及对应的 100 条未知经历，共 300 条序列。每对共用背景、位置、物体大小与帧数：首帧分别显示红色或蓝色方块，随后 2–6 帧完全遮挡；未知经历从首帧起就被遮挡。图像为 64×64 RGB，遮挡期间场景固定，帧数不对应真实时间。可用 `--seed` 和 `--pairs` 调整生成量；输出目录必须新建或为空。

问题固定为：**“你此前观察到了什么颜色？从未看见则回答未知。”** 这里未知指观察信息不足，不使用生成器内部的隐藏颜色作为答案。

三种方法只接收从 PNG 重新读入的 RGB 图像，不接收路径、样本编号、配对或答案。`last_frame` 和 `last_seen` 共用一个固定颜色阈值识别器；前者只看最后一帧，后者记录最近识别到的颜色，每条序列重新置为未知。`always_red` 是恒猜红色的参照。

默认 300 条序列的结果如下，三列分别评分，避免混合未知样本掩盖错误：

| 方法 | 已见颜色正确（200 条） | 从未见过时答未知（100 条） | 红／蓝整对全对（100 对） |
|---|---:|---:|---:|
| 只看末帧 `last_frame` | 0% | 100% | 0% |
| 保留最近颜色 `last_seen` | 100% | 100% | 100% |
| 恒猜红色 `always_red` | 50% | 0% | 0% |

只看末帧得到 0%，是因为该识别器遇到完全遮挡会回答未知；它不是所有单帧算法的上限。对于末帧相同、红蓝均衡的成对已见样本，固定的确定性单帧方法最多答对一半，不能整对全对。恒猜参照的 50% 只针对 200 条已见样本。

输出包括：

- `preview.png`：一对红／蓝经历及未知经历的画面、答案和各方法结果。
- `manifest.json`、`frames/`：实验问题、条件、图片、标签和文件哈希；标签仅供评分。
- `predictions.json`：每条经历的答案、预测及失败的方法，可按编号查找错误图片。
- `report.json`：三项评分、当前运行的输入条件检查、验收、源码哈希与环境版本。仓库保存运行报告副本 [reports/occlusion-memory-v0.json](reports/occlusion-memory-v0.json)。

正式验收要求当前数据的首帧识别、全部隐藏帧无颜色、整段配对隐藏像素一致检查通过，并且历史方法三项评分均为 100%。测试另覆盖移除历史后失去答案、可见颜色更新、跨序列记忆清空、结果可复现和拒绝覆盖已有文件。

**这是一项固定颜色、单物体的规则实验。** 它检验历史信息和状态保存的作用，没有训练模型，也没有证明通用识别、想象、图像编辑或芯片效率。原始图片及完整报告保存在本地 `artifacts/`，不将全部生成图片加入 Git。

## Minecraft M0：离线数据检查

无需安装游戏、FPGA 或第三方 Python 库，在项目根目录运行：

```powershell
python -S software/minecraft_data.py examples/minecraft-offline.json
python -S software/test_minecraft_data.py
```

第一条命令只读检查样例，输出 JSON 摘要及输入文件的 SHA-256；无效输入返回退出码 1 并说明问题。第二条运行边界与反例检查，不训练模型。`-S` 禁用第三方 site-packages，验证这一步只依赖标准库。

[examples/minecraft-offline.json](examples/minecraft-offline.json) 是 **人工编写的格式样例**：3 个动作段、4 个状态、12 个合成 tick，最后一个记录状态到达目标。样例没有游戏截图，也没有验证其运动与 Minecraft 一致。检查器只接受 `minecraft-m0-v1` 的人工 `example` 数据，不能把它作为游戏训练集或 M1 实采验收器。

### 当前数据契约

JSON 字段以样例和 [software/minecraft_data.py](software/minecraft_data.py) 为准；每层对象严格检查字段，缺项或未知字段均拒绝。

| 字段 | 定义 |
|---|---|
| `schema_version / episode_id / split` | 固定版本 `minecraft-m0-v1`、非空轨迹标识、固定 `example` 分组 |
| `provenance` | 固定 `hand_authored`、`synthetic_tick`；`game_captured=false`、`physics_validated=false`、`server_tick=null`、`image_source=none` |
| `units / state_order` | 未归一化；位置为方块单位，速度为方块／记录 tick；状态顺序固定为 `[x,z,vx,vz]` |
| `action_order` | 固定 `[forward,back,left,right,idle]`，未来 one-hot 编码按此顺序；`idle` 表示松开控制，不保证速度立即归零 |
| `task` | 场景标识、中心坐标允许边界与障碍、目标中心／半径、固定朝向和统一干燥平地声明、动作段 tick 数、最大动作段数 |
| `states[i]` | `tick` 与四维 `value`；从 tick 0 开始，每个动作段末尾记录下一个状态 |
| `actions[i]` | `start_tick / end_tick / control / collision`；动作作用于 `[states[i].tick, states[i+1].tick)` |
| `terminated / truncated` | 最后一个记录状态首次到达目标时为 `true/false`；未到达且恰好耗尽动作预算时为 `false/true` |

动作数 N 必须为正且不超过预算，状态数必须为 N+1；动作区间与两端状态一一对应，固定步长、严格递增、没有空隙或重叠。样例的每段 4 个合成 tick 仅用于格式验证，不换算成秒，也不代表已选定游戏控制周期。

地图坐标按 `[xmin,zmin,xmax,zmax]` 记录。`center_bounds` 包含边界；`center_obstacles` 的严格内部禁止玩家中心进入，边界接触允许。它们描述的是**玩家中心的允许区域**，不是未经处理的方块外形；M1 必须结合实际玩家碰撞尺寸建立对应地图。

到达判据为记录状态的中心到目标的二维距离 `<= goal_radius`，不推断两个记录状态之间是否曾穿过目标。首版拒绝初始就在目标、到达后继续记录动作、预算尚未耗尽却声称超时，以及未完成的轨迹片段。最后一步同时耗尽预算并到达时优先记为到达。

所有状态、边界、目标和朝向必须是有限数；布尔值不能冒充数字或 tick。速度是人工填写的边界值，不强制等于相邻位置差除时间；`collision` 是动作区间内是否曾接触／受阻的人工布尔标签，不从两个端点推断。检查器不执行运动、碰撞或渲染；M1 需另行验证这些声明及标签来源，并冻结游戏版本、bot／服务端时间与图像对齐契约。

## 运行

在项目根目录执行：

```powershell
python software/tabletop.py --out artifacts/tabletop-baseline
```

需要 Python、NumPy 和 Pillow。缺少库时可自行安装：

```powershell
python -m pip install numpy pillow
```

默认生成训练 24 条、验证 6 条、测试 6 条轨迹，每条最多 48 个动作，图像为 64×64 RGB。可调整种子和步数：

```powershell
python software/tabletop.py --seed 42 --steps 24 --out artifacts/tabletop-seed42
```

输出目录必须不存在或为空；程序拒绝覆盖已有结果。再次运行时请使用新的目录。

## 任务与数据

固定俯视相机观察桌面方块。二维动作的每个分量在 `[-1, 1]` 内，控制加速度；时间步长为 `0.1`，包含摩擦及无弹性的轴分离碰撞。场景中有矩形障碍，按目标中心距离与目标半径判断到达。

首次到达目标时结束，否则达到步数上限后截断。每条轨迹满足 **N 个动作对应 N+1 个状态和图像**。

训练、验证、测试按完整轨迹划分，使用各自的种子与程序素材实例，不将同一轨迹的相邻帧拆到不同集合。程序素材实例的隔离不等于已经验证真实场景泛化。

```text
artifacts/tabletop-baseline/
├── manifest.json
├── episodes/
│   ├── train/{episode_id}.json
│   ├── val/{episode_id}.json
│   └── test/{episode_id}.json
├── frames/{episode_id}/{index:03d}.png
├── baseline_report.json
└── preview.png
```

`manifest.json` 记录数据清单；轨迹文件记录状态与动作；`preview.png` 用于快速检查画面；`baseline_report.json` 保存基线评估结果。

## 怎样理解结果

基线直接读取仿真真值状态，在预测步长 `H=1、4、8` 上比较开环位置误差：

| 名称 | 含义 |
|---|---|
| `state_hold` | 预测位置保持不变 |
| `constant_velocity` | 按当前速度外推 |
| `action_prior_no_collision` | 使用模拟器参数和动作的解析预测，忽略碰撞 |

开环预测期间不使用后续真实状态纠正预测。这些是 **状态级解析基线**，不是从图像学习的世界模型；不能将低误差解读为模型训练成功。

默认种子 `20261021` 的首批数据实际生成 36 条轨迹、975 次状态转移和 1011 张图像。以下为 6 条测试轨迹的预测终点位置 RMSE，单位为像素：

| 基线 | 1 步 | 4 步 | 8 步 |
|---|---:|---:|---:|
| 保持位置 | 1.966 | 6.928 | 11.804 |
| 恒速度 | 1.105 | 5.881 | 13.396 |
| 带动作、忽略碰撞的解析预测 | 0.488 | 3.595 | 8.964 |

对应有效窗口数量分别为 195、177、153；窗口有重叠，不作为独立重复实验。复现环境为 Python 3.13.12、NumPy 2.4.6、Pillow 12.3.0；完整指标与数据哈希由运行命令保存。

候选硬件工作量估算只计算假设网络的 MAC 数、INT8 权重等静态规模，不代表模型已经训练、定点数值已经验证，也不是 FPGA 延迟、功耗或实际时序结果。

**Nano Banana 尚未调用。** 当前图像和素材全部由程序生成。后续如引入 Nano Banana 外观素材，先只替换背景；位置、动作和碰撞真值仍来自仿真。生成图片本身不作为物理真实性依据。

## P2：首轮视觉预测模型

模型使用两帧图像估计 `(x, y, vx, vy)`，再把这个估计和候选动作输入小型残差 MLP，连续预测未来状态。CNN 初始化器有 70,556 个参数；预测网络为 `6 → 64 → 64 → 4`，含 4,868 个参数。它是**受物理状态监督的紧凑预测模型**，尚非自监督 latent JEPA，也没有动作规划模块。

使用项目局部环境，可复用 P1 已安装的 NumPy/Pillow：

```powershell
python -m venv --system-site-packages .venv
python -m pip --python .venv/Scripts/python.exe install torch==2.14.1 --index-url https://download.pytorch.org/whl/cpu
.\.venv\Scripts\python.exe software/visual_predictor.py --data artifacts/tabletop-baseline --out artifacts/visual-pilot --epochs 80 --seed 20261022
```

若受限运行环境中的 `ensurepip` 失败，可先用 `python -m venv --without-pip --system-site-packages .venv` 创建环境，再执行上面的 `pip --python` 命令。输出目录同样要求新建或为空。

本轮为 CPU、2 线程、固定种子、80 轮试训。按验证集 8 步终点位置误差选择第 21 轮 checkpoint，然后评估 6 条测试轨迹。训练有 609 个窗口，验证 141 个窗口；测试各步长的结果如下，单位均为终点位置 RMSE 像素：

| 初态来源与预测方法 | 1 步 | 4 步 | 8 步 |
|---|---:|---:|---:|
| 两帧 CNN 初态＋学习转移 | 14.249 | 13.739 | 12.537 |
| 同一 CNN 初态＋保持位置 | 13.959 | 12.913 | 11.862 |
| 真值初态＋学习转移（诊断） | 1.883 | 4.972 | 8.058 |
| 真值初态＋已知动作公式、忽略碰撞（诊断） | 0.496 | 3.644 | 9.044 |

所有方法均使用同一批 `t ≥ 1` 窗口，数量依次为 189、171、147，所以不能直接与 P1 的 `t ≥ 0` 总表比较。完整报告还包含图像初态＋恒速度／已知动作公式、真值初态＋保持位置／恒速度，以及逐轨迹和碰撞窗口结果。

**本轮未通过视觉预测的性能关卡。** 图像初始化的位置 RMSE 为 14.469 像素，完整视觉链路没有超过同图像初态的保持位置基线；真实初态下的结果仅用于定位瓶颈。测试集仅 6 条轨迹、单个训练种子，不构成广泛泛化证据。

训练期间允许使用初始与未来真值状态作为监督，并额外从训练真值初态展开预测；正式图像推理只读取 `image[t-1]、image[t]` 与待执行动作，不读取未来图像、真值状态，也不调用物理仿真器代替网络展开。checkpoint 选择只看验证集。

输出位于 `artifacts/visual-pilot/`：

- `checkpoint.pt`：验证集选出的模型权重。
- `history.json`：全部训练损失与验证误差。
- `report.json`：相同窗口的 8 种对照、逐窗口误差、数据与源码哈希、环境及参数规模。

仓库中的 [reports/visual-pilot.json](reports/visual-pilot.json) 保存本轮精简报告；生成数据和权重留在本地，可通过命令重建。本轮实测环境为 PyTorch `2.14.1+cpu`，其余库版本同 P1。报告中的 `training_seconds` 包含训练、验证和最终测试评估，不代表纯训练性能。预测核的乘加计数只是工作量统计，尚未完成量化或 FPGA 性能验证。

## Minecraft 到 RTL 的推进规划

本节是 2026-10-22 制定的计划，参数与门槛为首版提案，不是已完成的实验。先做**固定小地图中的绕障到达目标**：平坦、统一地面、静态墙体、固定目标与相机朝向，只允许前、后、左、右、静止；暂不包含跳跃、冲刺、挖掘、建造或战斗。

建议使用 Java Edition，由 [Mineflayer](https://github.com/PrismarineJS/mineflayer) 接收状态和发送动作；客户端、服务端、Java、Node.js 与 Mineflayer 的具体版本在联通测试通过后一起锁定。当前尚未安装或验证这套环境。桌面模型仅复用评测思路和部分代码，不直接沿用权重或动作物理参数。

### 模型与计算分工

| 部分 | 首版选择 | 后续变更条件 |
|---|---|---|
| 状态预测 | 动作条件残差 MLP，先用游戏状态训练与诊断 | 先检查状态是否充分，再决定是否扩充输入 |
| 图像初始化 | 两帧截图 CNN，先在 PC 上运行 | 定位有歧义时先尝试有限历史帧，再比较 GRU |
| 长期记忆与关系建模 | 首版不引入 Transformer | 只有明确任务需求和对照结果支持时才增加 |
| 生成式视觉素材 | Nano Banana 可选，用于纹理变化实验 | 基础视觉链路通过后再接入，单独记录成本与素材版本 |
| 硬件加速 | 通过软件验证后的 MLP 多候选、多步预测 | 软件模型改变时重新评估算子、存储和接口 |

```text
PC：Minecraft → 状态读取／截图 CNN → 候选动作生成
                                      ↓
RTL：初态与动作存储 → 多步调度 → 共享 MLP 计算核 → 候选终态
                                      ↓
PC：候选评分 → 只执行第一段动作 → 重新观察并规划
```

状态先试 `(x, z, vx, vz)`，五种动作使用 one-hot 编码；由此得到的候选网络是 `9 → 64 → 64 → 4`，与桌面的 `6 → 64 → 64 → 4` 不同。网络宽度、残差缩放和采样周期均须用 Minecraft 数据验证后冻结。如果朝向、着地状态或地面材质仍在变化，应锁定这些条件或补入输入，不能用扩大网络掩盖缺失状态。

固定地图中，绝对坐标可能让模型记住墙的位置，因此首版只宣称该地图内的预测能力。要测试新布局，需先定义模型可以获得的局部地图或视觉上下文。第一人称相似画面也可能无法唯一确定位置，CNN 失败时先检查观测歧义和时间对齐。

### 阶段与验收

| 阶段 | 交付物 | 完成条件 |
|---|---|---|
| M0：数据契约与离线样例 | 状态、动作、时间、轨迹文件格式；地图边界与到达、碰撞、超时定义；小型人工样例与检查器 | 无需安装游戏即可检查 N 个动作对应 N+1 个状态；拒绝错序、缺项和无效数值。样例不作为游戏物理证据 |
| M1：游戏联通与采集 | 锁定环境、固定地图、重置与采集程序、独立轨迹数据；确定图像来源 | 重置、五种动作、碰墙与停止均可复现；记录实际动作区间与状态来源，检查丢帧和服务端位置修正；图像须对应受控实体视角 |
| M2：状态 MLP 与闭环 | 游戏数据训练的 MLP、解析对照、开环与闭环报告 | 同输入、同窗口比较预测误差；同候选集合、评分器与预算比较闭环结果，达到下列软件目标 |
| M3：截图 CNN 与外观实验 | 截图到状态的模型、完整视觉闭环报告 | 推理只用过去／当前截图与候选动作；同视觉初态的简单对照与完整链路均受评测，达到相同软件目标 |
| M4：定点参考 | 冻结的模型、权重与数据版本；整数推理与导出向量 | 明确缩放、位宽、累加范围、舍入、饱和与状态反馈；完整多步展开及动作选择通过量化目标 |
| M5：RTL 仿真与实现评估 | 模块规格、Python 整数参考、Verilog、testbench、实际工具报告 | 逐项匹配整数参考；握手、复位、候选隔离通过；选定器件与约束后再验收资源及实现后时序 |
| M6：FPGA 板测与 ASIC 评估 | 板上对照、端到端耗时；有库和约束后的 ASIC 报告 | 有板卡后验证输出与链路；ASIC 综合、布局布线、功耗估算分别标明实际工具与证据范围 |

每阶段先检查上一阶段证据，通过后才推进。**没有 FPGA 不影响 M0–M4 与 M5 的仿真；实际综合和时序评估取决于工具与目标器件。** M0 已有上文的人工样例与只读检查器；下一阶段 M1 在游戏环境可用后进行，不先生成占位 RTL。

### 数据与软件目标

- 动作按明确的 tick 区间执行，持续长度在 M1 小样本检查后冻结；预测步长先比较 `H=1、4、8` 个动作段。依据 [Mineflayer API](https://github.com/PrismarineJS/mineflayer/blob/master/docs/api.md)，`physicsTick` 可用于 bot 侧事件计数，`setControlState` 用于控制输入；bot 的物理 tick 不等于服务端权威步进，不能用固定墙钟等待冒充严格同步。
- Mineflayer 的状态与控制接口不等于原版客户端截图。M1 单独确定受控实体的图像来源并检查时间对齐；若先用项目说明中单列的 [prismarine-viewer](https://github.com/PrismarineJS/mineflayer#see-what-your-bot-is-doing)，须标明是该渲染器的画面，并记录渲染器版本及素材，不能称为原版客户端截图。
- 首批拟采集训练 150、验证 30、测试 50 条完整轨迹，每条最多 100 个动作段；覆盖自由移动、停止、贴墙与转角。按轨迹与初始条件隔离，截图与状态记录各自的时间对应关系、来源和数据哈希。位置误差统一使用游戏世界坐标的方块单位，速度单位及归一化参数记入数据契约；新地图与新纹理另列测试范围。
- 训练与调参只使用训练／验证集；先登记门槛，再运行保留测试集。若查看测试结果后修改模型，下一轮须登记新版本并准备新的保留测试，不能持续对同一测试集调参。
- 开环比较保持状态、恒速度及可用的动作解析对照，声明各自允许读取的信息。各方法共享初态、动作和预测起点，展开时均不回灌未来真值。首版目标为 **H8 位置 RMSE 比最强可比简单基线降低至少 10%，H1 退化不超过 5%**；三个训练种子各自判定通过，另报均值、碰撞误差与逐轨迹结果。近零基线的绝对容差在保留测试前登记：H1 允许该绝对容差内的变化；若 H8 基线已低于该容差，应报告简单方法已足够好，不作为学习预测优势过关。
- 闭环先比较朝目标移动的简单策略，再在相同规划器中仅替换预测器。每个训练种子使用相同的 50 个独立评测初始条件；每条最多 100 个动作段，未到达即超时。三个种子各自须达到 **到达率至少 80%，比最强可比简单对照提高至少 10 个百分点，碰撞率不增加**。碰撞率为发生过至少一次碰撞的轨迹数／50，具体接触判据和异常运行处理在保留测试前冻结。同时报告动作段数、计算耗时和轨迹级不确定性；开环改进不能替代闭环验收。若简单方法已足够好，应保留简单方法，并在验证集上重新评估任务难度。
- 视觉阶段分别报告 CNN 状态误差、真值初态＋MLP、图像初态＋MLP、相同图像初态＋简单预测器。游戏坐标可以作训练监督和评测标签；正式视觉推理不读取坐标或未来图片。
- Nano Banana 仅作为可选外观素材来源；先将生成纹理用于游戏渲染，再采集游戏画面和状态。生成图片不直接作为碰撞或运动标签。原始外观与变化外观分别评测，不能用静态改图替代连续游戏数据。[官方图像生成说明](https://ai.google.dev/gemini-api/docs/image-generation)

上述百分比是待实验检验的目标，不是收益保证。未通过时先检查采集对齐、状态充分性和数据覆盖；只有有限历史仍不足且存在证据时，才比较 GRU，模型变更后重新检查硬件范围。

### 定点与 RTL 的边界

M4 前先测实际预测核、CNN、游戏采集和传输耗时，决定是否值得硬件化。若预测核不是主要耗时，可以做数值与 RTL 教学验证，但不声称整机加速。初始预算可试 `K=16` 个候选、`H=8` 步；这只是负载样例，不是已经冻结的端口上限或吞吐承诺。

定点优先试 INT8 权重和 INT16 状态／激活；累加位宽按每层范围推导，偏置尺度、舍入及饱和逐项定义。首版量化目标为：相同窗口下 H8 RMSE 相对浮点增加不超过 5%，闭环到达率下降不超过 5 个百分点。最终规格同时登记基线误差接近零时的绝对容差，逐层记录饱和，禁止累加器溢出，并检查完整反馈链。

RTL 首版只接收一个作业的初态及 K 条动作序列，复用共享乘加核、权重存储与激活缓冲；每个候选保留当前状态，完整算完一步后再提交更新，输出候选终态与标识。PC 负责终态评分，首版不宣称支持需要整段轨迹信息的评分；若软件验收证明必须增加中间输出或风险状态，需在 M4 前调整契约。

生成前须冻结数据布局、合法长度、任务／候选标识、权重装载边界、时钟复位和接口时序。按规格 → Python 整数参考 → RTL 推进，每个模块附同名规格与时序图；严格检查 `compile、ast、readability、comment、naming、profile、testbench、toolchain`，外部仿真与综合证据分别记录。

验收至少包括：与整数参考逐项一致；随机输入间断与输出回压；输出停顿期间数据和标识稳定；连续作业和候选间无串扰；复位中断丢弃当前作业并清除旧输出；权重推理期间不被改写。仿真通过不代表已通过综合或实现后时序。

有板卡后分别测计算核与包含传输、编码、游戏交互的端到端延迟。只有实测电源数据才报告实测能耗。ASIC 评估须先确定工艺库、角点、存储映射和真实约束；不会从 FPGA 工作量直接推断 ASIC 面积或功耗。

推进顺序为 **M0 → M1 → M2 → M3 → M4 → M5 → M6**。每个小阶段验证后在当前分支提交并尝试正常推送，保留数据、权重和报告的版本关系；推送失败时明确区分本地提交与 GitHub 状态。
