# 小球检测工程 Python 功能仿真

这是可运行的软件工程模型。输入图像真实经过颜色分类、ROI、4×4同色二维区域分离、单球追踪或计数门、叠加、RGB96到RGB128打包、双帧缓存和RGB显示。检测框、颜色、坐标和数量来自像素运算，不读取模拟场景中预设的球位置或身份。

工作目录为 `E:\project\ball\python_sim`，当前不是Git仓库。沿用现有Python、NumPy和OpenCV，未安装新依赖。

2026-10-19已与当前RTL的4×4区域语义同步；11项功能检查和3帧入口冒烟通过。框单元有最多约3像素边界量化，硬件实际周期另有RTL/安路报告。当前不是实板准确率证明。

## 启动

双击本目录的 `启动模拟.cmd`，或在本目录执行：

```powershell
python main.py
```

默认打开流水线模拟场景，第一、二颗均为红球，后面依次为绿、黄、绿、黄；一轮真值为红2、绿2、黄2、总6。第一颗红球在计数门内停72帧，期间有2帧完全不可见。场景循环，计数持续累计；C可清零。

按1切单球追踪，按2切流水线计数，M切原图/掩膜，T切普通/严格阈值，C清零，空格暂停，Q或Esc退出。暂停不会推进检测或空门确认。

也可以用相同算法处理实际输入：

```powershell
python main.py --mode track --source 0
python main.py --mode count --source "D:\videos\balls.mp4"
```

摄像头编号按本机实际设备选择。视频和摄像头输入统一缩放到1280×720；坐标也按此尺寸报告。请使输送带接近水平，并按下述条件布置计数场景。

无窗口执行两种场景并录制、留日志：

```powershell
python -B test_simulation.py
python -B main.py --headless --mode both
```

单球默认240帧，流水线默认360帧；可用`--frames`指定长度。完整360帧流水线运行会检查实际计数是否与六球真值一致，失败即报错。MP4记录采用24fps时间轴，不代表本机实测处理速度。

## 模块与数据流

| 文件 | 已实现的行为 |
|---|---|
| `scenes.py` | 只生成摄像头端RGB像素，包含球面明暗、高光、运动、停留、短暂不可见和白灰/蓝色干扰物 |
| `pipeline.py:segment` | 9位以上整数RGB比较，黄色优先、互斥三色分类、半开ROI |
| `pipeline.py:ComponentRAM` | 双帧4×4颜色支持单元，四邻接有界队列，面积/尺寸/填充率筛选、候选及拒绝诊断 |
| `pipeline.py:TargetTracker` | 一个单球轨迹槽、2帧确认、位置关联、1/2帧暂失、第3帧重新搜索 |
| `pipeline.py:GateCounter` | WAIT_CLEAR/READY/ARMED/HOLD/BLOCKED，方向、迟滞、颜色锁定、空门确认、异常及32位饱和计数 |
| `pipeline.py:Pipeline` | 配置代号、旧帧拒绝、结果帧快照、逐帧模块调度 |
| `pipeline.py:render` | 检测框、中心十字、坐标、掩膜、ROI、计数门、各色和总数，以及门状态 |
| `video_io.py` | early与valid分开的四像素输入、逐拍打包参考模型、等价批量打包及双帧缓存 |
| `main.py` | 输入源、窗口按键、录制、逐帧CSV、阶段图和汇总结果 |
| `test_simulation.py` | 无新测试框架的可运行断言检查 |

模拟器的正式图像接口为`Pipeline.process(rgb)`，其中RGB数组必须为720×1280×3、uint8。返回显示帧、本帧统计、本帧结果、显示帧来源及DDR字数。颜色编号沿用基底：0未知、1红、2黄、3绿。

模拟场景和检测器隔离：`scenes.py`生成RGB，`main.py`把RGB交给`Pipeline`。检测器不知道球数真值、运动路线或掉检安排。最终六球真值仅用于运行完成后的独立验收。

## 计数与几何条件

默认ROI为`[64,1216)×[160,640)`，门区为`[544,736)×[160,640)`。计数线X=640，中心X≤624在上游区，X≥656在下游区；两者都必须处于门内。

先确认球在上游2帧，随后中心到下游时计一次。球在画面内停留、门内停留或有1～2帧漏检，都不能自动重新计数。整门连续空3个完整检测帧后，下一颗同色球可重新计数。门是否清空同时观察原始分割像素和候选框，避免框过滤失败直接解锁。

当前要求球沿水平单列从左到右，互不接触；全画面可有多颗同色球，门内同时最多一颗。球之间还要让整门空出至少3帧。完全漏检3帧以上、同色接触、连通背景或复杂遮挡不保证正确去重；可观察到的多球占门、短间距再进入或候选溢出会阻塞计数。不能自动识别的违规不承诺全面报警。

中心是检测框几何中心，不是像素质心。这里不加入CNN、卡尔曼滤波、多目标永久ID或逐像素无损连通域。

## 查看内部证据

`output/track`和`output/count`中包含：

- `simulation.mp4`：软件显示输出录制。
- `frame_trace.csv`：每个输入帧的候选中心、状态、门空帧数、分色计数、计数事件、显示帧编号和DDR字数。
- `01_input.png`、`02_mask.png`、`03_components.png`、`04_hdmi_output.png`：一个检查点的输入、掩膜、二维区域和缓存输出。
- `pipeline_overview.png`：四阶段并列对照。各阶段带有管线延迟，并非同一时刻的零延迟叠图。
- `summary.json`：实跑帧数、计数事件、最终分项、同时候选数及软件执行耗时。

`output/test_report.json`记录功能检查结果。CSV中的`count_event`是检测帧生成的事件；显示会晚于该事件，不应把两列帧编号混为一谈。

## 与FPGA工程的对应边界

模型对应AWB及Gamma之后的检测RGB；实际USB/视频直接使用其现成RGB，并不重放传感器ISP；USB摄像头/视频输入不是SC520的RAW10或MIPI仿真。原厂CSI、demosaic、AWB模拟电路效应、DDR控制器和HDMI物理编码尚不在本模型内。

实际执行全部图像功能，但4×4统计由NumPy批量执行，连通遍历由有界队列执行，同步RAM读改写与处理器没有逐时钟调度。交互路径的打包使用与逐组参考模型相同的批量字节变换；独立检查通过valid空拍、帧首及行帧尾验证逐组模型。720P每帧230400个RGB96组、172800个DDR128字，打包不改变像素字节顺序。

显示明确使用上一完整检测帧的快照，再经过一帧缓存；这是固定的软件时序模型；硬件密集场景可能额外等待一个显示帧，summary中已单独标注。模式/阈值/清零递增配置代号，旧代统计不能更新新状态。已经进入显示帧缓存的旧画面会自然排空，不被追溯修改。

OSD用OpenCV字体渲染，未复刻RTL字模逐像素输出。功能检查通过不代表RTL周期仿真、综合资源、握手时序、真实传感器准确率或实板HDMI已验证。

2026-10-19预测版：TargetTracker同时保存实测目标与显示目标。同色/宽高比关联，优先选择预测位置候选，实测位置窗用于急停回退；连续观测估速、4像素死区、每轴±2×max_move限幅，显示框整体平移一帧并裁剪ROI。漏检两帧冻结，第三帧搜索。显示中心是估计值；计数器仍使用原FrameStats实测候选。新增RTL对照206帧990快照，实际板上运动效果另行验证。
