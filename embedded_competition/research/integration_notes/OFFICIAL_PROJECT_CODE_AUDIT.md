# 安路官方人脸识别基线工程 RTL 审计

审计对象：`baseline_lab1`（官方 `lab_hd_1_mipi_hdmi` 的未修改工作副本）  
审计日期：2026-09-08

## 1. 总结

当前官方工程没有导致构建失败的“缺失模块”。工程文件登记的 52 个 HDL、约束和 IP 条目都存在，Tang Dynasty 已完成综合、布局、布线、静态时序分析和位流生成；综合错误和未解析黑盒均为 0。最终建立时间 WNS 为 `+0.629 ns`，保持时间 WNS 为 `+0.020 ns`。

工程确实存在三类容易被误认为缺模块的问题：

1. `user_source` 中保留了未加入工程的旧版本、替代算法和调试模块；
2. 当前链路中有输入悬空、位宽不一致、未使用信号和注释掉一半的旧支路；
3. DDR、FIFO、RAM、HDMI 等生成或加密 IP 内部产生大量综合告警。

这些问题需要分级处理。建议保留 `baseline_lab1` 作为可回退基线，在新的开发副本中先做不改变功能的接口清理，再对复位、帧错误和数据打包模块做带仿真的功能修改。不要以“清零所有 Warning”为目标，也不要修改厂商生成或加密 IP 的内部 RTL。

## 2. “缺少模块”的核对结果

### 2.1 当前顶层需要的模块均能解析

综合日志已经成功展开以下主链路：

```text
MIPI D-PHY -> CSI 解包 -> RAW10 解包 -> 流格式整理
-> demosaic -> AWB -> 96/128 位打包 -> video_in
-> DDR 控制器 -> video_out -> HDMI mixer/transmitter/PHY
```

`design_top_wrapper`、`raw10_unpacket_2lane`、`isp_top`、`data_96bit_to_128bit`、`video_in`、`video_out`、`mc_to_user_interface`、DDR 和 HDMI 模块都已展开。工程不存在“顶层实例化了某模块，但综合器找不到定义”的错误。

### 2.2 同名或近似文件造成了误判风险

工程实际登记的是：

- `isp/data96_128/data96_128.v`，其中定义了当前使用的 `data_96bit_to_128bit`；
- 根目录还存在 `data_96bit_to_128bit.v`，但它没有加入当前 `.al` 工程；
- 当前使用根目录的 `awb.v` 和 `signal_delay.v`，`isp/awb/` 中还保留了另一套未登记版本；
- `csi_unpacket_2lane.v`、`raw10_unpacket_2lane.v`、`uial2axis.v` 也存在不同目录的重复或变体。

因此后续修改前必须先查 `.al` 中登记的真实路径。修改了未登记副本时，工程仍能正常构建，但行为不会改变，这比真正缺文件更难排查。

### 2.3 未加入工程的文件是备选功能，不是当前依赖

典型文件包括：

| 文件/模块 | 判断 | 是否加入当前工程 |
|---|---|---|
| `isp/BLC/BLC.v` | 黑电平校正候选模块 | 暂不加入；设计 ISP 插入点时再评估 |
| `auto_white_balance.v` | 旧式 AWB 路径 | 不加入；当前已经有 `awb.v` |
| `raw8_to_rgb888.v` | 旧 RAW8 转 RGB 路径 | 不加入；当前是 RAW10+demosaic 路径 |
| `video_cuttting.v` | 旧裁剪模块 | 不加入；当前 `image_correction` 已承担 1024×600 窗口整理 |
| `ps_wrapper.v` | 处理器系统接口候选 | 当前无软核/PS 链路，不加入 |
| `mipi_rx_error_detect.v` | 帧完整性检测雏形 | 不能直接加入，需先修正后再接入 |

`mipi_rx_error_detect.v` 内部硬编码期望 `832` 行，与当前 `600` 行图像不一致，而且实例化了工程中不存在的 `cwc1` 调试核。因此它不是可以直接补回的“漏加模块”。若需要错误恢复，应删除或条件编译调试实例，把尺寸参数化，并为计数器补齐复位和测试。

## 3. 当前 RTL 中需要处理的问题

### 3.1 优先级 A：建议在开发副本中修正

| 位置 | 现象 | 当前影响 | 建议 |
|---|---|---|---|
| `isp_top.v` 顶层连接 | `I_tdest` 悬空；输入端口 `O_tready` 接到无驱动的 `S_ISP_O_tready`；输出 `I_tready` 未使用 | 仿真中会出现 `X/Z`；综合器把无驱动值按 0 处理，掩盖接口问题 | 当前流水线没有真正实现停顿，应明确采用固定速率流：`I_tdest=10'd0`、下游 ready 固定为 `1'b1`，并在接口注释中说明“不支持 backpressure” |
| `image_correction.v` | 输入 `O_raw_tready` 未连接；模块内部给未声明的隐式网 `I_raw_tready` 赋值；实例没有名称 | ready 信号对数据通路没有作用，层次调试困难 | 删除这组假 ready 接口，或显式固定为 1；给实例命名。建议同时加入 ``default_nettype none`` 类检查，防止隐式网继续出现 |
| `raw10_unpacket_2lane.v` | `I_camera_black_level`、FIFO 和 RAW8 信号仍在声明，但使用它们的整段逻辑已被注释 | 产生约 103 条告警；当前 RAW10 输出不受影响 | 删除旧 RAW8/FIFO 声明和黑电平端口，或先把黑电平端口显式接 `10'd0` 以保持接口兼容 |
| `raw10_unpacket_2lane.v` | 当前生效的计数器、有效信号和输出寄存器没有使用 `I_rst_n` | 复位后最初若干拍在 RTL 仿真中可能为 `X`，硬件上电瞬态也不确定 | 为当前活动寄存器补同步或异步复位；先用 RAW10 字节序列测试平台确认数据相位不变 |
| `data96_128/data96_128.v` | `I_rst_n` 已声明却完全未使用，计数器和输出无复位 | 仿真启动时状态不确定，必须依赖 `I_96b_valid=0` 才回到计数 0 | 加复位；验证每 4 个 96-bit 输入生成 3 个 128-bit 输出，且行首、帧首与首个输出数据的关系保持正确 |
| `mc_to_user_interface.v` / 顶层 | 模块输出写掩码为 32 bit，顶层及 DDR wrapper 为 16 bit | 当前恒为 0，截断没有功能影响，但接口含义不一致 | 把接口统一为 DDR wrapper 的 16 bit，并继续明确驱动 `16'd0` |
| MIPI 顶层连接 | `LANE_NUM=2` 时给 `I_lane_invert` 连接 `4'b0000` | 高两位被截断；因为全 0，所以当前无功能影响 | 改为 `2'b00` 或按 `LANE_NUM` 参数构造常量 |
| 摄像头寄存器配置 | 24-bit 寄存器项接到 32-bit 端口；`I_ag-16` 形成 32-bit 表达式后接 7-bit 端口 | 当前高位都是 0，增益范围为 16～89，功能上基本安全 | 显式切片/扩展和使用定宽常量，消除工具相关的隐式截断 |

### 3.2 优先级 B：应设计后修改，不能直接接线

#### MIPI 错误没有进入帧缓存恢复逻辑

MIPI D-PHY 已输出 `S_lane_error[1:0]`，顶层也生成了 `S_lane_error_any`，但该信号没有被使用。与此同时，`video_in` 的 `I_mipi_rx_error` 被固定为 `1'b0`，导致 `video_in` 中“错误帧不推进写指针、覆盖错误帧”的代码永远不会执行。

这是有实际功能含义的缺口，但不能把 `S_lane_error_any` 直接接到 `video_in`：

- lane error 可能只是一个短脉冲；
- `video_in` 在 DDR 时钟域读取错误状态，存在跨时钟域问题；
- `video_in` 需要的是“这一整帧是否出错”的结论，而不是瞬时 lane 状态。

建议新增一个参数化的帧错误锁存模块：在 CSI 时钟域从帧开始到帧结束累计 lane、包头和行数错误，在帧边界冻结结果，再用握手或 toggle 同步到 DDR 时钟域。模块先用正常帧、少行、lane error 脉冲和连续错误帧做仿真。

#### ready 信号只是形式上的传递

`demosaic`、`bilinear_interpolation`、`raw_matrix_3x3_buffer` 和 `awb` 中的 ready 大多只是组合透传，没有任何时序逻辑用 ready 停住数据、有效信号、行缓存地址或像素计数。因此这些端口不是完整的 AXI4-Stream backpressure 实现。

当前摄像头链路本来就是不可暂停的固定像素率流水线，最安全的短期方案是把下游 ready 固定为 1，并把接口称为“valid 数据流”。如果后续接入会阻塞的 NPU、DMA 或跨时钟 FIFO，必须整体加入缓存和停顿传播，不能只补一根 ready 线。

#### DDR 命令接口有保守假设

`mc_to_user_interface` 仅在 `I_mc_app_rdy` 与 `I_mc_app_wdf_rdy` 同时为 1 时弹出命令。读命令其实不需要等待写数据通道 ready，这会降低读请求机会，但通常不破坏正确性。模块还没有使用 FIFO 的 `valid` 输出，而是依赖该 FIFO 的 show-ahead/读时序配置。

现阶段不要直接改这段握手。应先建立 DDR 控制器接口模型，覆盖读、写、ready 随机拉低、FIFO 接近满、读写切换等情形，再决定是否把读写条件分开。

#### 复位释放跨多个时钟域

顶层把 `S_pll_lock` 直接作为 `S_rst_n`，并送往 24 MHz、CSI、DDR 和 HDMI 等多个时钟域。PLL lock 用于解除系统复位的思路合理，但每个时钟域都应做到异步置位复位、同步解除复位，避免解除瞬间的亚稳态或不同寄存器离开复位的周期不一致。

这是稳定性改进，不适合在没有回归测试时一次性全改。建议先封装统一的 reset synchronizer，再逐时钟域替换和仿真。

### 3.3 优先级 C：可清理，但不会改善当前功能

- 顶层的 `S_aux_50m_clk`、`S_10m_clk`、`S_vi_128b_*` 没有使用；
- 大量 `S_dbg_*` 黏滞状态、同步寄存器和常量调试信号没有连接到最终可观察输出；
- `S_lane_error_any` 当前只被赋值，不被消费；
- `image_correction` 的 `I_raw_frame_end` 当前未使用；
- `hdmi_tx` 中 `S_pll_lock` 未驱动，却被用于一个按键消抖实例的复位；该按键消抖输出本身也未使用；
- `hdmi_tx` 的 I2S 接收器输出没有被使用，顶层又把音频输入固定为 0；
- 顶层 `I_button` 声明为 `inout`，但 RTL 只读取它，若引脚约束没有特殊要求可改为 `input`；
- 注释掉的逻辑分析仪实例和旧算法支路可移到单独的 debug/legacy 文件，而不是长期留在活动模块内。

综合器通常会删除这些逻辑，所以它们主要增加阅读和维护成本。可在第一轮无功能清理中移除，但每批清理后仍应重新综合并对比顶层端口、资源和时序。

## 4. 不建议修改的告警

综合告警中数量最多的部分来自 DDR PHY、生成 RAM/FIFO、divider 和加密 HDMI/MIPI IP。例如：

- DDR PHY 的初始化、校准和未使用配置位；
- RAM 双口模板中未使用的 `dib` 位；
- divider 生成网表的未驱动内部位；
- 加密控制器内部锁存器、异步置位/复位和未连接配置端口。

这些模块已经参与完整实现并通过最终时序。除非重新生成 IP 或获得安路官方修订版本，否则不要手工编辑其 RTL。

物理实现还报告了三类需要上板观察的时钟告警：I2C 内部分频 `scl_clk` 同时驱动时钟和控制端，摄像头 24 MHz 网同时驱动时钟和数据端，以及一条标记时钟使用局部布线。当前最终时序通过，因此先保留基线；若上板出现摄像头初始化偶发失败，再把 I2C 分频时钟改为时钟使能，并重新规划摄像头时钟输出。

## 5. 推荐修改顺序

### 第一轮：无功能变化清理

1. 从官方基线复制出开发工程，保留原基线和原位流；
2. 给 `image_correction` 实例命名；
3. 将所有悬空输入显式连接为确定常量；
4. 修正 2/4、16/32、7/32 和 24/32 位宽连接；
5. 删除确定未使用的顶层线网、未消费的调试寄存器和 RAW8 注释残留；
6. 重新综合、实现并对比顶层 I/O、资源、时序和位流生成结果。

### 第二轮：小模块可靠性

1. 为 `raw10_unpacket_2lane` 和 `data_96bit_to_128bit` 写自检测试平台；
2. 在保持输出序列不变的前提下补复位；
3. 明确帧首相对首个有效 128-bit 数据的周期定义；
4. 把固定速率视频流接口写成项目统一规范。

### 第三轮：错误恢复和时钟域

1. 重写并参数化 MIPI 帧错误检测；
2. 正确跨时钟域传递“上一帧出错”状态；
3. 为各时钟域加入同步解除复位；
4. 建立 DDR 请求随机阻塞仿真，再优化读写握手。

### 第四轮：上板验证后再决定

1. 验证摄像头 reset 极性和上电延时，确认 `O_cam_rst=1'b1` 是否符合原理图与传感器手册；
2. 观察 MIPI lane error、CSI 帧行计数和 DDR 丢帧情况；
3. 连续运行并检查黑屏、花屏、撕裂、颜色异常与帧停顿；
4. 仅在出现相应现象时处理物理时钟告警。

## 6. 当前建议

现在值得修改，但应只先做第一轮无功能清理，并在独立开发副本中进行。复位、ready、帧首对齐、MIPI 错误恢复和 DDR 握手都具有功能含义，必须在测试平台覆盖后分批修改。官方 `baseline_lab1` 应保持不变，作为后续定位“新问题来自算法还是来自底层链路”的对照工程。
