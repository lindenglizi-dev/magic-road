# 人脸项目软硬件接口规范

## 1 使用范围

本规范用于第一周第五天冻结电脑端参考程序、RTL仿真和后续FPGA实时链路之间的数据定义。电脑不参与最终设备的实时检测。Python负责生成测试输入和黄金结果；FPGA负责实际视频流处理、检测、识别和OSD显示。

推荐将第一版检测模块接在DDR视频读出之后、`hdmi_mixer`之前。该位置已经是一拍一个RGB888像素，算法和OSD可共用HDMI像素时钟，能够减少数据重排和跨时钟域工作。

```text
DDR video_out
  │ RGB888 + valid + frame_start + line_end
  ▼
face_detect_top
  ├── 原视频透传 ──► hdmi_mixer ──► HDMI
  └── 人脸结果 ────► hdmi_mixer画框与文字
```

## 2 软件到RTL仿真的图像文件

### 2.1 图像约定

| 项目 | 固定定义 |
|---|---|
| 有效图像尺寸 | 1024 × 600 |
| 像素格式 | RGB888 |
| 扫描顺序 | 从上到下逐行，每行从左到右 |
| 坐标原点 | 左上角 `(0, 0)` |
| 像素文件 | 每行一个24位十六进制像素，格式为 `RRGGBB` |
| 总行数 | 1024 × 600 = 614400行 |

例如，第一行前三个像素依次为红、绿、蓝时，文件开头应为：

```text
FF0000
00FF00
0000FF
```

Python转换脚本为 `pc_face_detection/export_frame_hex.py`。RTL测试平台使用 `$readmemh` 读取该文件。

### 2.2 黄金结果JSON

检测程序输出的人脸统一使用以下字段：

```json
{
  "frame_id": 1,
  "image_width": 1024,
  "image_height": 600,
  "faces": [
    {
      "x": 120,
      "y": 80,
      "width": 160,
      "height": 180,
      "person_id": 0,
      "score": 0.86
    }
  ]
}
```

坐标覆盖范围采用左闭右开定义：`x <= pixel_x < x + width`，`y <= pixel_y < y + height`。`person_id=0` 表示陌生人或尚未识别，已登记人员从1开始编号。

## 3 FPGA像素流接口

第一版统一使用固定速率有效流，不设计ready反压。

| 信号 | 方向 | 位宽 | 含义 |
|---|---|---:|---|
| `I_clk` | 输入 | 1 | HDMI像素时钟 |
| `I_rst_n` | 输入 | 1 | 低有效复位，在`I_clk`域同步解除 |
| `I_rgb_valid` | 输入 | 1 | 当前周期像素有效 |
| `I_frame_start` | 输入 | 1 | 与一帧第一个有效像素同周期 |
| `I_line_end` | 输入 | 1 | 与每行最后一个有效像素同周期 |
| `I_rgb888` | 输入 | 24 | `[23:16]=R`、`[15:8]=G`、`[7:0]=B` |
| `O_rgb_valid` | 输出 | 1 | 透传视频有效 |
| `O_frame_start` | 输出 | 1 | 与透传视频第一像素对齐 |
| `O_line_end` | 输出 | 1 | 与透传视频最后像素对齐 |
| `O_rgb888` | 输出 | 24 | 透传或处理后视频像素 |

如果算法产生流水线延迟，数据、`valid`、`frame_start`和`line_end`必须延迟相同周期。算法不能只延迟像素而不延迟控制信号。

## 4 FPGA检测结果接口

第一版限制最多输出4张人脸。每张脸可复制一组以下字段；初次联调先实现face0。

| 信号 | 方向 | 位宽 | 含义 |
|---|---|---:|---|
| `O_result_valid` | 输出 | 1 | 新结果脉冲，载荷在该周期有效 |
| `O_frame_id` | 输出 | 16 | 结果对应的输入帧编号 |
| `O_face_count` | 输出 | 3 | 当前结果中的人脸数量，范围0～4 |
| `O_face0_x` | 输出 | 12 | 左上角x坐标 |
| `O_face0_y` | 输出 | 12 | 左上角y坐标 |
| `O_face0_width` | 输出 | 12 | 框宽度 |
| `O_face0_height` | 输出 | 12 | 框高度 |
| `O_face0_person_id` | 输出 | 8 | 0为陌生人，1～254为登记人员 |
| `O_face0_score` | 输出 | 16 | Q0.16分数，`65535`代表接近1.0 |

`O_result_valid`出现时，OSD一次性锁存整组结果。没有新结果时，输出载荷可以保持不变。OSD默认保留结果不超过3帧；连续3帧未收到更新时清除旧框，防止人脸离开后框仍停留。

## 5 与当前官方工程的连接

检测模块从顶层以下信号取数：

```verilog
.I_clk         (S_hdmi_pixel_clk),
.I_rst_n       (S_hdmi_rst_n),
.I_rgb_valid   (S_hdmi_de),
.I_frame_start (S_hdmi_user),
.I_line_end    (S_hdmi_last),
.I_rgb888      (S_video_rd_data)
```

接入前必须用计数器检查一帧是否恰好包含600行、每行1024个有效像素，并确认`S_hdmi_user`和`S_hdmi_last`是否与有效像素同周期。如果官方控制信号早一拍或晚一拍，应在适配层完成对齐，检测核心内部继续遵守本规范。

`hdmi_mixer`目前没有人脸结果输入，需要增加上述结果端口以及矩形边框判断。第一版只画绿色框；身份文字和多目标支持放到后续迭代。

## 6 第五天执行步骤

### 上午

1. 团队评审并固定1024×600、RGB888、坐标原点、框范围和人员编号定义。
2. 用红绿蓝白四个像素的小测试图检查Python输出的通道顺序。
3. 用`export_frame_hex.py`把一张1024×600图片导出为614400行HEX。
4. 建立黄金结果JSON，并人工检查框坐标没有越界。

### 下午

1. 将`face_detect_top_stub.v`加入单独仿真工程，不加入官方基线。
2. 测试平台读取HEX，产生`valid`、`frame_start`和`line_end`。
3. 检查RTL收到的第一个、行末和帧末像素与Python一致。
4. 让桩模块在帧末输出固定框，检查`result_valid`只出现一个周期。
5. 用软件读取RTL结果，检查字段与黄金JSON格式一致。
6. 冻结接口文档和测试向量，第二周只替换桩模块内部算法。

## 7 当天验收标准

- 任何队员都能把指定图片转换为HEX；
- HEX恰好包含614400个像素；
- Python和RTL对首像素、行末像素、末像素的RGB解释一致；
- RTL能够完整接收1024×600一帧，计数无多一拍或少一拍；
- 固定测试框能够通过结果接口送出；
- 接口文档写明时钟、复位、位宽、有效条件、坐标范围和异常行为；
- 官方`baseline_lab1`保持不变。
