本次完成：Stem 权重和 down2 halo 的合法写请求在接收沿登记，下一沿写入原存储。原 3 项内部 setup 违例降至 0 项；本候选成为新的内部物理诊断基线。严格交付门及外部接口/原始复位入口仍未通过，不能称整个 CNN 或板级系统通过。

## 代码与实现范围

- [Stem 调度器](rtl/road_stem_tile_scheduler.v)：新增权重 pending/address/data，原 loader 继续更新接收游标与 loaded；独占写进程提交原 `reg_weight`。
- [down2 调度器](rtl/road_down2_tile_scheduler.v)：新增 halo pending/address/data，下一沿提交原 `reg_halo`。
- 算术核、共享前端接口、ROM/预取器及 SDC 均保持原内容；现有 DW 权重的 pending 结构继续保留。
- [逐拍契约](逐拍实施契约.txt)及两个同名 `_spec.md`/周期图明确：loaded 表示接收完整；末项提交可与 start 同沿，首次 PREPARE/STORAGE 读取在其后。ready 与单拍 start 不增加等待，接收 II=1。
- 合法 pending 与新非法项同沿时，提交先前合法项，新项置原故障且不入队；复位清 pending 和完整性，存储不清零。

修正前次提案：顺序游标在接收沿推进，而不是等写入后再推进；否则连续 A/A+1 会被误判为乱序。存储提交与接收完整性必须区分。

## 为什么这次有效

[综合写口核查](physical/gate_commit_check.json)确认两个 pending 触发器真实保留。旧来源/装表/ready/合法性长链不再直接驱动 RAM WE：

- Stem 分布式 RAM 的写使能在寄存器后为 1 级 LUT；3 个 ERAM 写使能直接来自 pending。
- down2 halo 写使能在寄存器后最多 2 级 LUT。
- 这些写使能的上游只含本地 pending、已寄存写地址及复位，不含原外部请求控制链。

候选第一次综合/布局后，旧脚本所引用的 `i_advance_dup_2` 已不存在。精准对象检查停止，尽管 TD 退出码为 0，程序仍因缺少 route/报告完成标记判为失败；该目录保留。

之后直接从这个新候选的 `before_replication.db` 续接，没有重新综合。只读查询确认推进网当前 850 个负载、ROM 当前最大同族分支 50 个负载；按既有 128/16 阈值机制进行原生分流并布线。两组控制网的 LUT 配置、有效输入与全部负载集合前后相等，见 [控制网核查](physical_attempt2/control_replication_check.json)。850 个负载分为 11 组，50 个分为 4 组，无漏失、重复或额外负载。阈值不是最终每组负载的硬上限。

资源和时序来自这次实际实现，不能把改善全部归因于新增寄存器本身；综合映射和布线也发生了变化。
