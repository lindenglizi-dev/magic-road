# RoadYOLO 控制边界修复与时序对比

本轮已完成批准的两处 RTL 修改、同向量功能回归、安路综合布局布线和新路由网表功能回归。内部 setup 失败端点由 135 个减到 2 个，最差裕量从 −1.119 ns 改善为 −0.222 ns，但仍不能宣布 100 MHz 内部时序通过。外部接口时序与严格门禁也未闭合。

## 修改位置与行为边界

当前候选只保存在 `control_operand_hold_20261009`，实际物理比较基线是 `dw_weight_load_timing_20261009`。中间实验 `postprocess_control_timing_20261009` 另行冻结，未拿它代替有物理结果的基线。工程不是 Git 仓库，版本依靠目录隔离和哈希记录。

| 文件 | 本轮修改 | 不变部分 |
|---|---|---|
| [road_dynamic_postprocess.v](rtl/road_dynamic_postprocess.v) | PRE 选择器用 `flag_pre_buffer_valid` 提前选择后继，不再由 `flag_pre_accept` 驱动选择链 | 真正装载仍受原 refill 条件限制；队列出队、计数、握手不变 |
| [road_mac_probe.v](rtl/road_mac_probe.v) | A0 未接受输入时保持激活、权重、偏置和 mask，不再清零这些宽数据 | valid、first、last 仍清零；复位仍清零全部 A0 寄存器；A1 起算术代码逐字节不变 |

八个 RTL 文件中仅上述两个有差异，六个保持原样，端口未改，新增流水级为 0。具体差异见 [rtl_change.diff](rtl_change.diff)，文件哈希见 [scope_check.json](scope_check.json)。没有修改生产工程、训练、生成位流、上板或写 Flash，也没有新增时序例外。

这不是所有内部寄存器逐拍相等的修改：空拍数据现在可能保留旧值。等价要求是有效事务的数值、顺序、故障和取消行为不变；无效拍不能累加、入队或发布故障。PRE 只有在原条件允许装载时才采用预选结果，停顿期间缓冲 payload 仍保持。

## 实际资源与全量内部时序

目标为 PH1P35MDG324、速度等级 −3、100 MHz；实际综合顶层为 `road_dynamic_overlap_low_io_top`，包含 DW/PW 调度、MAC、动态重定标、SiLU、缓存及窄口验证壳，共八个 RTL 文件。构建脚本和约束沿用冻结版本，自动引脚仅用于隔离诊断。

资源不能可靠拆分为壳与内核，因此统一标为“含验证壳”。此顶层没有完整权重 ROM、完整 DDR 视频链和整网调度；这些数字不是整机资源。

全量路径报告覆盖率为工具报告的 100%。内部检查包括 13,633 个 setup、15,206 个 hold、3,420 个 recovery 和 3,420 个 removal 记录；只有两条 setup 为负。寄存器子集 setup 最差为 +0.103 ns，但这个子集排除了部分 DSP 路径，不能据此宣布全部内部通过。报告记录的最坏角点包括 setup/recovery 的 slow_m40c，以及 hold/removal 的 fast_m40c；hold 记录另含 fast_125c。工具按端点选择最坏结果，这不等于每个角点均有一份独立全量导出。

原 DW 权重写控制的 41 个映射端点继续通过，最差 setup 为 +3.842 ns。详见 [physical_analysis.json](physical_analysis.json)、[path_diagnosis.json](path_diagnosis.json) 和 [全量内部及外部路径](physical/coverage_100000_all_paths.timing)。

## 剩余两条路径及原因

两条路径均从 `ptr_pw_meta_read_reg[1]_syn_7.clk` 出发，分别到 MAC 的 `mult12_syn_57.ce[0]` 和 `mult13_syn_57.ce[0]`，裕量为 −0.222 ns 和 −0.028 ns，角点为 slow_m40c。

最差路径的实际组合链为：

```text
PW 元数据读指针
  → MAC 结果队列 fault 位的分布式 RAM 读取
  → 输入资格控制 LUT4
  → 接受条件 LUT5
  → MAC DSP 输入寄存器 CE
```

最差路径数据延迟为 9.429 ns，其中逻辑单元 1.289 ns、布线 8.140 ns，布线占约 87%；仅三级逻辑，最大扇出 38。最后一段接受许可到 DSP CE 的布线就占 4.284 ns。因此剩余问题主要是队头故障资格参与的同拍接受控制及其物理分发，不是乘法本身或 SiLU 数值计算。

本轮原有 PRE/DSP 数据输入违例族已不在负裕量列表中，但宽数据保持让接受条件映射到 DSP CE，CE 仍需正常签核。不能把“从数据端转到使能端”当成整个控制问题已解决。

下一项最小候选是仅对 MAC 本地两位 `ptr_result_read` 增加厂商 `preserve` 属性，尝试阻止它与 runner 的 `ptr_pw_meta_read` 跨层合并，使结果队列读头与故障资格逻辑由本地寄存器发起。两者复位值相同，均在同一个 MAC 结果接受事件前进；当前映射结果队列读取使用了 runner 指针。预计代价是保留两位 FF，但是否改善布局必须重跑验证，属性本身不保证时序通过。

这比另加 fault 缓存或改信用旁路更小。不能简单把 fault 延迟一拍，否则可能允许本应取消的后续事务进入；也不能删除满队列时同拍 pop/push 的信用旁路，否则可能增加气泡。后续候选必须覆盖同时 push/pop、队列空满、末组故障和复位，保持 II、延迟与原子故障语义；若做不到，应先申请契约变更。本轮没有追加该项修改。

原始证据：[负裕量路径](physical/coverage_100000_violations.timing)、[DSP 全量端点](physical/dsp_all.timing)、[ERAM 全量端点](physical/eram_all.timing)。

## 外部接口与严格门禁

外部接口仍有 15 个 setup、40 个 hold、4 个 removal 失败端点，最差外部 setup −1.540 ns、hold −1.161 ns。继续保留原诊断 I/O 延迟，没有编造板级延迟，也没有放宽约束。需要真实外设契约后才可签核。

`check_timing` 中 no_clock、组合环、无效约束、no_path 等计数为 0；仍保留一个 generated clock 与 master 连接检查，以及 DSP mode/signed dummy 对象记录，不能把报告覆盖率当成所有检查都已闭合。详见 [约束检查](physical/check_timing_verbose.rpt)、[异常对象](physical/abnormal_targets.rpt)。

## 恢复与失败记录

冻结输入检查覆盖 2,090 个文件，中间候选另查 95 个文件，均未变化。源码、数据库、约束和工具日志保留在本目录；最终状态见 [status.json](status.json)，主要证据哈希见 [evidence_hashes.json](evidence_hashes.json)。

本轮工具层失败均保留：接口文档首次生成受 Windows 长路径限制，改用本目录短输出路径后成功；受限环境的路径读取失败在获准的本地执行方式下重试成功；首次收集脚本引用不存在的旧 `collect.py`，改用已有历史收集器后成功。这些不是数值回归失败，记录不删除。接口说明和周期图保存在 `rtl` 子目录。

最终结论：批准的两处最小修改有效，功能与周期保持，资源略减；当前候选仍不得晋升生产。接下来应针对两条 MAC CE 控制路径做局部修复，而不是重复改算术、继续微调 SiLU或凭本小块结果缩网。
