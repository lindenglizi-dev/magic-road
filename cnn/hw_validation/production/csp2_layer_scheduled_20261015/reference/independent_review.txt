Schedule, addresses, and exact counts
-------------------------------------
The RTL traverses the complete 72x128 frame as 18x32 = 576 tiles in strict stage-major order:

  DW0   55,296 tasks, 110,592 8-byte groups, 110,592 outputs
  PW0   36,864 tasks,  73,728 8-byte groups, 110,592 outputs
  DW1   55,296 tasks, 110,592 8-byte groups, 110,592 outputs
  PW1   36,864 tasks,  73,728 8-byte groups, 110,592 outputs
  fuse  73,728 tasks, 221,184 8-byte groups, 221,184 outputs
  total 258,048 tasks, 589,824 groups, 663,552 outputs

The task loops, output address calculation, tile counters, stage barriers, and TB constants agree with those totals. DW scheduling presents four output rows by two column groups by twelve channels per tile: three normal 5-pixel horizontal windows plus one separately issued 3-pixel tail per row/channel. PW presents sixteen pixels by four output-channel groups per tile; fuse presents sixteen pixels by eight groups.

The inspected address mapping agrees with graph_artifacts/graph.json and the Python audit:

  source / down2.pw.conv  0x035b4000, 221,184 bytes
  DW0                     0x035ea000, 110,592 bytes
  PW0 / residual.00       0x03605000, 110,592 bytes
  DW1                     0x03620000, 110,592 bytes
  PW1 / residual.01       0x0363b000, 110,592 bytes
  fuse / csp2.out.conv    0x03656000, 221,184 bytes

The source channel-half aliases, residual aliases, and concatenated fuse view are used semantically rather than allocated as extra physical buffers. The historical diagnostic base 0x03600000 lies inside the DW0 allocation and must not be treated as independent scratch memory.

Cache, parameter, and port behavior
-----------------------------------
The single 432-byte activation cache is reused mutually exclusively by all stages. DW fill covers a padded 6x6x12 tile and supplies the normal 3x5 union or the 3x3 tail locally. PW0/PW1/fuse use at most 384 activation bytes per tile. The RTL assembles each 8-byte activation group from one 8-bit local cache read per cycle; it does not expose or imply an eight-byte physical activation-memory read port.

Parameter storage is resident and loaded once per output-channel group per tile before task reuse: four 192-bit weight groups = 96 bytes, one 248-bit parameter group = 31 bytes, plus one 16-byte logical read line. Together with the 432-byte activation cache this is 575 bytes, excluding tags, metadata, control state, and implementation overhead. Four ERAMs equal 10,240 raw bytes only as a capacity comparison; banking, ports, inference, placement, utilization, and timing remain unproved until synthesis/implementation.

The logical memory interface permits one outstanding aligned 16-byte read, registers request and response identity, accepts variable response latency, and faults on response-address or error mismatches. This is a logical cache-line contract, not a claim about the native DDR endpoint. The parameter service is independently backpressured and checked for kind/layer/group identity and data stability. The external core interface is ready/valid; no convolution, bias, activation, or accumulator arithmetic is duplicated inside the client. Each result retires only with the corresponding external write, with address, tag, byte-mask, and duplicate checks.

Lifetime and visibility behavior
--------------------------------
The implementation and TB preserve the intended lifetimes: the source remains readable through fuse; DW0/DW1 survive until their following PW stages; residual.00 survives through DW1 and the PW1 bypass; residual.01 survives through fuse. A stage becomes a legal read source only after the matching barrier has made it visible. The TB snapshots written visibility at barriers rather than making golden intermediate tensors live memory sources.

Testbench independence and negative cases
-----------------------------------------
The TB loads only the immutable source image into live input memory. Intermediate memories start poisoned and are populated only by accepted DUT writes. Golden arrays are used by scoreboards, not by the live intermediate-read path. Independent per-address write maps, duplicate checks, exact task/group/stage totals, final completeness checks, and visibility checks cover all 663,552 output bytes.

The negative cases are connected to active protocol events:

  * wrong read-response address on an actual returned line;
  * wrong parameter-response layer on an actual parameter response;
  * wrong barrier layer on an actual barrier request;
  * forced wrong core-output address while core_output_valid is asserted.

These cases must prevent normal completion or writes as specified. NEGATIVE_ACC is different: it deliberately corrupts the expected accumulator comparison, not the DUT datapath or DUT input. It is a valid checker-sensitivity regression, but it must not be described as a DUT fault injection.

The TB now counts accepted parameter requests and emits them in each per-stage ledger and CSP_LAYER_RUN record. The statically expected request counts are [27,648, 4,608, 27,648, 4,608, 13,824], total 78,336. It likewise emits the expected logical line-read counts [30,210, 20,736, 16,748, 13,824, 27,648], total 109,166. However, the frozen finish_frame checks do not assert either array against those exact values, and tb_contract.json/runner receipt validation does not declare them as expected fields. Therefore a ModelSim PASS will measure and expose read/parameter reuse, but it does not by itself mechanically prove the exact reuse counts; the emitted ledgers must be compared with these values before making that claim. This is a verification-closure gap, not a static RTL mismatch.
